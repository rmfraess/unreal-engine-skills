# Fixed-preset Windows PIE baselines

Verified with UE 5.8.2 and the live VibeUE/EditorToolset services. Rediscover contracts after integration changes. Project authority controls ownership, budgets, packages and persistence.

- Reuse native floating PIE and an explicit StartPIE startTransform; read the actual possessed camera, lens and viewport dimensions. Requested Play settings and desktop dimensions do not establish output size. A tested Windows floating window added two vertical pixels; verify the exact owned window rather than relaxing an exact-resolution assertion. If an offset repeats after relaunch, prefer calibrating the native window request and verifying a fresh launch over retaining an external resize workaround. Label that calibration as reference-machine-specific, not a universal offset.
- Separate start completion from warm-up. If StartPIE times out, inspect pie_running/health before retrying; a timeout can leave a healthy running session. A tested alternative is warmupSeconds=0 followed by a native scenario wait. Never block the game thread with Python sleep.
- Use the session-only PerformanceService background-throttling switch for unattended measurement and restore its prior state. t.IdleWhenNotInForeground alone is not this Editor setting.
- For preset persistence, store appropriate native config defaults, apply through transient console commands for the current session, then relaunch and read back WITHOUT calling the apply function. Preserve launcher-cleaned logs and reconcile all processes it targets first. Runtime CVars matching before a relaunch do not prove persisted config.
- Read actual internal resolution, not arithmetic alone. A GPU profile's TemporalSuperResolution event reported actual input/output rectangles; an explicit fractional scale can ceil a dimension. Suppress ProfileGPU UI before unattended use, retain and restore its prior setting, and capture outside measured windows.
- Use native csvprofile start/stop around tick-driven waits. r.GPUCsvStatsEnabled=1 enables per-pass GPU CSV statistics in the tested build (CsvProfiler.cpp command-line setup confirms this CVar). Preserve its previous value. CSV frame, Game, Render, RHI and GPU timers are separate; do not sum CPU and GPU or interpret a near-zero RenderThreadTime counter as zero total parallel-renderer work.
- Parse native CSV structure before calculating percentiles. With [HasHeaderRowAtEnd], counters can be appended during capture: early rows are shorter and the final header extends the initial header. Verify prefix/index stability; metrics already present initially need no invented padding. Do not treat repeated headers/metadata as frames, silently truncate new columns, or discard hitches. Leave a small runnable parser/percentile check and verify actual capture duration/count.
- Keep per-workload CSV windows separate from an untrimmed Insights trace. CSV start/stop, readback, capture, warm-up and tool activity can appear outside those windows. Retain and disclose out-of-window spikes rather than claiming an entire trace is hitch-free from trimmed-window maxima. Validate plugin duration fields against capture brackets and frame timestamps before calling them elapsed capture duration.
- Record profiling/recording overhead honestly: which channels/counters/observers ran, whether overhead was separately calibrated, and which intervals support the claim. OS memory counters at 1 Hz prove sampled peaks, not sub-second high-water guarantees; match the process identity and bound samples to the actual scenario timestamps. Adapter-wide dedicated usage and per-process dedicated usage are different metrics.
- Keep raw traces in the project's durable archive, with byte counts and streaming SHA-256 checks; Saved is staging. Preserve failed checks and meaningful rejected captures. A stationary diagnostic view is not canonical-anchor, worst-case, traversal, content-scale, or final-creative acceptance.
